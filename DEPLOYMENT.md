# Deploying CollabIQ

CollabIQ has three parts that deploy separately:

| Part      | Host          | Why |
|-----------|---------------|-----|
| Frontend  | Render Static | Static Vite build served from Render's CDN, free tier |
| Backend   | Render        | FastAPI with no serverless time limit (the AI call takes ~17s) |
| Database  | Neon          | Managed PostgreSQL, free tier |

Both Render services are described by `render.yaml`, so a Blueprint deploy
creates them together. Deploy in this order: **Database → Backend → Frontend**
(each needs the previous one's URL), then set `FRONTEND_ORIGINS` last.

## Live environment

| Part     | URL |
|----------|-----|
| Frontend | <https://collabiq-web.onrender.com> |
| Backend  | <https://collabiq-api.onrender.com> |
| Database | Neon project `collabiq`, region `aws-us-west-2` |

> Render's free tier sleeps after inactivity, so the first request after a
> pause takes ~30s to wake the backend up.

---

## 1. Database — Neon

1. Create a project at <https://neon.tech> (name it `collabiq`).
2. Copy the connection string:
   ```
   postgresql://USER:PASSWORD@ep-xxx.neon.tech/collabiq?sslmode=require
   ```
3. Change the scheme to the psycopg2 form this app uses — replace
   `postgresql://` with `postgresql+psycopg2://`:
   ```
   postgresql+psycopg2://USER:PASSWORD@ep-xxx.neon.tech/collabiq?sslmode=require
   ```
   Keep this string — it is `DATABASE_URL` for the backend.

Tables are created on the first backend deploy: the build runs
`alembic upgrade head`, and `database/migrations/env.py` reads `DATABASE_URL`
from the environment.

---

## 2. & 3. Backend and frontend — Render

**New → Blueprint**, pick the `mariam-khalife/collabiq` repo. Render reads
`render.yaml` and proposes both services: **collabiq-api** and
**collabiq-web**. Fill in the variables marked `sync: false`:

| Service        | Variable            | Value |
|----------------|---------------------|-------|
| `collabiq-api` | `DATABASE_URL`      | the Neon string from step 1 |
| `collabiq-api` | `LLM_API_KEY`       | your Google Gemini API key |
| `collabiq-api` | `FRONTEND_ORIGINS`  | the frontend URL — set after the frontend is up |
| `collabiq-web` | `VITE_API_BASE_URL` | the backend URL, e.g. `https://collabiq-api.onrender.com` |

`SECRET_KEY` is generated by Render; there is nothing to fill in.

`VITE_API_BASE_URL` is inlined by Vite **at build time**, so changing it
requires a rebuild of `collabiq-web`, not just a restart. If it is unset the
bundle falls back to `http://127.0.0.1:8000` and the deployed site cannot
reach the API.

---

## 4. Connect the two (CORS)

Set `FRONTEND_ORIGINS` on `collabiq-api` to the deployed frontend origin
(comma-separated if there is more than one), then **redeploy the backend** —
Render stores the new value but does not restart the service on its own, so
the running process keeps the old CORS config until it is redeployed.

Verify:

```bash
curl -i -X OPTIONS https://collabiq-api.onrender.com/auth/register \
  -H "Origin: https://collabiq-web.onrender.com" \
  -H "Access-Control-Request-Method: POST"
```

A correct setup returns `200` with an `access-control-allow-origin` header
echoing the frontend origin. A `400` with no such header means
`FRONTEND_ORIGINS` is wrong or the backend has not been redeployed.

---

## Environment variable reference

**Backend (`collabiq-api`):**

| Variable           | Example |
|--------------------|---------|
| `DATABASE_URL`     | `postgresql+psycopg2://user:pass@ep-xxx.neon.tech/collabiq?sslmode=require` |
| `SECRET_KEY`       | (Render generates) |
| `LLM_API_KEY`      | your Gemini key |
| `FRONTEND_ORIGINS` | `https://collabiq-web.onrender.com` |

**Frontend (`collabiq-web`):**

| Variable            | Example |
|---------------------|---------|
| `VITE_API_BASE_URL` | `https://collabiq-api.onrender.com` |
